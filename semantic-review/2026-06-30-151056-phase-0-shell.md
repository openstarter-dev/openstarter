# Phase 0 · SaaS 启动模板外壳:三 shell 路由 + 主题 + 文档(whole-branch)

把原本只有 ASCII 首页 + 健康灯的空壳,改造成可直接换皮的 Indie SaaS 模板外壳。核心是用三个 pathless layout 把营销页、登录页、应用后台彻底隔开:`_marketing`(SSR,Header/Footer + Landing/Pricing/Legal)、`_auth-pages`(`ssr:false`,居中卡片 + 已登录反向跳 `/dashboard`)、`_app`(`ssr:false`,Sidebar 外壳 + 未登录跳 `/login`,取代旧的 `_auth/`)。配套:next-themes 主题 + `__root.tsx` 内一段预水合 FOUC 脚本、无外壳的 404/Error 逃生页、收敛到 `lib/` 的 brand/pricing/faq 常量、重写的 README 与新增 CUSTOMIZE.md。跨任务接缝干净,鉴权流转闭合无环,品牌单点贯通全站。

**Watch for:**
- 移动端 App 抽屉:从抽屉内 UserMenu 选「Settings」后抽屉不关闭,新页面被遮罩盖住,需手动 Esc/点遮罩才解除(confirmed,Minor)。
- 两个手写抽屉都没有 focus-trap / 焦点归还 / body 滚动锁 / `role="dialog"`(confirmed,Minor a11y)。
- `_app`/`_auth-pages` 守卫是 `ssr:false` 的客户端 UX 门,不是安全边界;真正的鉴权仍靠 API/session 层(本期未改动)(confirmed,信息项)。

**Verdict**: Ship with follow-ups

## High-level view

三个 shell 的鉴权流转是这次最关键的接缝,经核验闭合无环:未登录访问 `/dashboard` → `_app` 跳 `/login`,而 `/login` 所在的 `_auth-pages` 此时查到无 session 不再跳转;已登录访问 `/login` → `_auth-pages` 跳 `/dashboard`,`_app` 查到有 session 放行;表单提交成功也 `navigate` 到 `/dashboard`。两个守卫都 `ssr:false`、都用 `authClient.getSession()`,行为一致。

Marketing Header 在 SSR 下用 `authClient.useSession()` 做三态 CTA:服务端与客户端首帧都是 `isPending`,渲染同一个同尺寸 Skeleton,因此无水合错配;session 只在客户端 mount 后解析,SSR 不发鉴权请求。

主题端到端自洽:FOUC 脚本的 storageKey 与类切换跟 next-themes(`attribute="class"`)对齐,配 `suppressHydrationWarning` 与两个组件的 `mounted` 守卫;除两处抽屉遮罩 `bg-black/50` 外全走语义 token,`bg-sidebar`/`bg-popover`/`bg-card` 等在 `@openstarter/ui` 的 globals.css 里 light/dark 双套齐全。

品牌单点贯通:`apps/web/src/` 内无 `openstarter` UI 字面量,显示名一律经 `BRAND_NAME` 流到 Header/Footer/Sidebar/`<title>`/auth-pages/404/Error;旧 `_auth/`、`components/header.tsx`、旧 `user-menu.tsx` 已删且无悬挂引用。

真正要跟进的只在 App 组件层:移动抽屉与其内 UserMenu 的关闭联动缺一条线,两个抽屉的可达性(焦点/滚动锁)仍是占位级 —— 都不阻断合并。

### 三 shell 的鉴权流转闭环(无重定向环)

```
                 _marketing (SSR, 无守卫)
                      /  /pricing  /privacy  /terms
__root ──┬── _auth-pages (ssr:false)  beforeLoad: 有session → /dashboard
         │        /login
         └── _app (ssr:false)         beforeLoad: 无session → /login
                  /dashboard  /settings
```

把两条守卫对接逐路推演,均终止:未登录打开 `/dashboard`,`_app/route.tsx` 抛 `redirect({ to: "/login" })`;落到 `/login` 时 `_auth-pages/route.tsx` 查 `getSession()` 无 `data`、不跳转,渲染表单 —— 不成环。已登录打开 `/login`,`_auth-pages` 抛 `redirect({ to: "/dashboard" })`;落到 `/dashboard` 时 `_app` 查到 `data`、放行 —— 不成环。`sign-in-form.tsx:33` 与 `sign-up-form.tsx:35` 登录成功都 `navigate({ to: "/dashboard" })`,与 `_app` 守卫衔接。两个守卫都 `ssr:false`、都用 `authClient.getSession()`,无 SSR/CSR 行为分叉。

一处非对称:`_app/route.tsx` 的 `beforeLoad` 返回 `{ session }`、`_app/dashboard.tsx` 经 `Route.useRouteContext()` 取 `session.data?.user.name ?? "there"`(对 `data` 可空有兜底);而 `_auth-pages` 不回传 session(login 页用不上)。无害,但两个守卫的返回形态不一致,后续若有人指望 auth-pages 的 context 会扑空。

### Marketing Header 的 SSR 三态鉴权 CTA

`_marketing` 是唯一不设 `ssr:false` 的组,Header 里 `AuthCta` 用 `authClient.useSession()`。SSR 首帧与 hydrate 首帧都是 `isPending`,渲染同一个 `<Skeleton className="h-8 w-32" />`,二者一致不触发水合告警;session 只在客户端订阅后解析,服务端不发鉴权请求,Skeleton 尺寸与解析后的按钮簇接近、layout shift 很小。这套用法与被删的旧 `Header→UserMenu`(同样在 SSR 根里调 `useSession`)同源,非本期新引入的风险面;烟雾测试营销页能正常出 SSR 文案,印证这条路径不崩。

### 移动端 App 抽屉:抽屉内 UserMenu 选 Settings 不关闭抽屉

`mobile-topbar.tsx` 抽屉里放了两块:`SidebarNav`(`mobile-topbar.tsx:63`,拿到 `onNavigate={() => setOpen(false)}`,点 Dashboard/Settings 会关抽屉)与 `UserMenu`(`mobile-topbar.tsx:66`,没有任何关闭回调)。UserMenu 的「Settings」是 `DropdownMenuItem render={<Link to="/settings" />}`,点击导航到 `/settings`,但 `MobileTopbar` 在 `_app` 布局里保持挂载、`open` 仍为 `true`,于是 `fixed inset-0 z-50` 的抽屉继续盖在新页面上,用户得手动按 Esc 或点 `bg-black/50` 遮罩才能看到 `/settings`。

同一目的地 `/settings` 经两条路可达(SidebarNav 会关、UserMenu 不会),体验不一致。「Sign out」走到 `/`、离开 `_app`、`MobileTopbar` 卸载,所以那条没问题 —— 缺口只在停留于 `_app` 内的 Settings 链接。桌面 Sidebar 无遮罩,不受影响。修法:给 `UserMenu` 暴露导航后回调,或在 `MobileTopbar` 里订阅路由变化把 `open` 归位。

### 两个手写抽屉:可拆分性与可达性

营销 Header 抽屉(右滑入)与 App MobileTopbar 抽屉(左滑入)是两份独立手写实现。两者承载内容不同(营销 nav+CTA vs 应用 nav+用户卡)、方向不同,**各自独立是可接受的**,不算硬性 DRY 违规;真正重复的是骨架 —— `useEffect` 监听 Escape、`fixed inset-0`、`bg-black/50` scrim `<button>`、`w-72` 面板各写了一遍,后续若要收敛抽成共享 Drawer 原语即可一并去掉重复的 Escape 监听。

可达性两个抽屉都缺:没有 focus-trap(Tab 会跑到被遮罩的背景内容)、关闭后不归还焦点到触发按钮、打开时不锁 body 滚动、容器无 `role="dialog"`/`aria-modal`。打开按钮带了 `aria-expanded`、scrim 是带 `aria-label` 的真 `<button>`(键盘可关)是基本盘,但上面几项需补齐才达模板水准。装饰图标 `aria-hidden` 也不齐:`features`/`pricing`/`footer`/`sidebar-nav`/`user-menu`/`faq` 都加了,而两个抽屉的 `<Menu/>/<X/>` 与 `ThemeToggleIcon` 的 `<Sun/>/<Moon/>` 没加(都在带 `aria-label` 的按钮内,危害小,建议与已认定的 mobile-topbar Minor 一并处理)。

### 主题端到端

`THEME_SCRIPT` 读 `localStorage.getItem('theme')`(与 next-themes 默认 `storageKey='theme'` 对齐),按 `t==='dark' || ((t==='system'||!t) && prefers-dark)` 算出 `d` 再 `toggle('dark',d); toggle('light',!d)`,与 `ThemeProvider` 的 `attribute="class"` 同管两个 class 一致;值得确认的边界是 explicit `light` —— 两个分支都为假 → `light`,four-value(dark/light/system/缺失)全覆盖。`ThemeToggleIcon` 用 `resolvedTheme` 在 light/dark 间切,`ThemeMenuItems` 用 `DropdownMenuRadioGroup` 的 `value`/`onValueChange`(Base UI `Menu.RadioGroup` 契约,已核对组件确有此导出)写 system/light/dark;两者都用 `mounted` 守卫,未挂载时 toggle 固定 `Moon`、radio 选中态 `undefined`,避免 SSR/CSR 错配。代价是 dark 用户 hydrate 后会看到一次 `Moon→Sun` 图标翻转(纯视觉,计划里已声明接受)。

### 品牌单一来源与依赖收敛

`grep openstarter apps/web/src` 排除 `@openstarter/*` 导入后零命中,显示名全部经 `BRAND_NAME`;`BRAND_TAGLINE` 同时供 Hero H1 与 Footer tagline(改一处两处都变,符合设计)。删除面干净:`_auth/`、`components/header.tsx`、旧 `components/user-menu.tsx` 全删且无悬挂 import(grep 已确认)。依赖侧把 `lucide-react` 收进 catalog,`apps/web`(原 `^1.8.0` 解析到 1.21.0)与 `packages/ui` 统一到 `0.546.0`,消除同名包双版本 —— 这是本期唯一动到 lockfile 的跨包改动,与 UI 改动相关、无夹带。

### 客户端守卫不是安全边界(安全视角)

因本期触及鉴权流转,明确一句:`_app`/`_auth-pages` 的 `beforeLoad` 因 `ssr:false` 只在浏览器跑,是 UX 级门禁,不构成数据保护;绕过它直接打 `/api/*` 仍取决于 session 层是否独立鉴权。本期未改 `packages/api`/`packages/auth`(契约不动),该保护沿用既有实现,与旧 `_auth/`(同为 `ssr:false`)相比无回退。不阻断合并,但跟进时别把路由守卫当授权层。
